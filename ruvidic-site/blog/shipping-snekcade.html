From Side Project
to Google Play

Building the app turned out to be the easy part. Snekcade, a retro 8-bit game that teaches Python, was playable for weeks before it was launchable. This is the part nobody puts in the tutorial: payments, email, the domain, the Android wrapper, and the long list of declarations Google wants before anyone can install your app.

What Snekcade Is

Snekcade turns a Python course into eight pixel worlds and 42 short levels. Each level is a few swipes: read a tiny idea, predict what the code prints, put lines in order, then write real Python that runs on the phone. There is an arcade mode, daily review, a monthly league, trophies, and a final world where you build the logic of your own Snake game and then play it. The first worlds are free with no account. A subscription, the Snek Pass, unlocks the rest.

Technically it is deliberately small: a static progressive web app with no framework, a handful of serverless functions on Vercel, and Supabase for accounts and sync. Python runs in the browser through WebAssembly, so there is no code execution server to secure or pay for.

Payments: Plan B Is Part of the Plan

Selling software internationally from Serbia means you want a merchant of record: a company that sells on your behalf and handles VAT, invoices and chargebacks. My first choice reviewed the store and rejected it, with no reason given. The integration was finished and tested by then, which hurt.

I switched to Polar, which supports sellers in Serbia. Because the app only ever stored a normalized subscription row (status, renewal date, end date), swapping providers meant writing one new webhook handler and one checkout endpoint, not touching the game. A few rules kept that layer honest:

→
Checkouts are created server-side. The browser asks for a checkout with the signed-in user's token; the API key never leaves the server, and the user ID travels inside the checkout so the webhook knows who paid.
→
Every webhook is verified. Signature checked against the raw body, timestamps older than five minutes refused, so a captured request cannot be replayed.
→
Idempotent and order-aware. Each delivery ID is recorded once, and an event older than the stored state is ignored, so a late "updated" can never undo a cancellation.
→
Test mode can't leak. Test-mode events are ignored in production unless explicitly allowed. Otherwise anyone with a test card number gets a free subscription.
Lesson Keep the payment provider at the edge of the system. If your app logic only knows "is the Pass active until this date", a rejection from one provider costs you an evening, not a rewrite.

Email Without Paying for a Mailbox

An app with accounts needs two kinds of email: a public address people can write to, and reliable outgoing mail for sign-in codes. The registrar wanted a yearly fee for a mailbox I would barely use, and its DNS editor was locked behind a paid tier. So the domain's nameservers moved to Vercel, and the mail was split in two:

→
Inbound: a free forwarding service. A single alias on the domain lands in my normal inbox. No catch-all, so spam to random addresses simply bounces.
→
Outbound: a transactional email provider plugged into Supabase as custom SMTP, with SPF, DKIM and a DMARC record so sign-in emails reach the inbox instead of spam.
→
Branded templates: the default auth emails look like phishing. A small pixel-art header and one clear button fixed that, and the email stays tiny.

Android Without Rewriting Anything

The Play Store version is a Trusted Web Activity: a thin Android shell that opens the web app full screen in Chrome, plus the Play Billing bridge so subscriptions bought on Android go through Google. One codebase, two stores.

The shell only goes full screen if the website vouches for the app through a Digital Asset Links file containing the signing certificate fingerprint. The catch: with Play App Signing, Google re-signs the app with its own key. The fingerprint of the key you upload with is not the one users get, so the file needs both. Miss the second one and every user sees a browser address bar at the top of your "native" app.

The first uploads also bounced on requirements that change every year: the minimum SDK level for the browser helper library, the minimum Play Billing Library version, and the target SDK level for new apps. None of it was hard, but each one cost a build.

Gotcha After your first upload, copy the "App signing key certificate" fingerprint from the Play Console into assetlinks.json. In the newer console it lives under Protected by Play, then Play Store protection, not under the old App integrity page.

The Play Console Gauntlet

A new personal developer account starts with identity verification, a verified phone, and proof that you own a real Android device. Then the app itself needs eleven declarations before the first review. Most are a few clicks; a few deserve thought.

→
Reviewer access. Reviewers cannot create accounts, pay, or use free trials. Snekcade signs in with one-time email codes, which a reviewer can't receive. The fix: one dedicated review account that signs in with a password, with the subscription pre-enabled in the database. Everyone else still uses codes.
→
Data safety. Declare what the app really collects, even the boring parts: crash reports, the push-notification address, the league nickname. Processors acting on your behalf (hosting, database, payments) don't count as sharing.
→
Account deletion. In-app deletion is not enough; Google wants a public web page explaining how to delete an account and what is kept. I had to add one.
→
Target audience. Choosing any age group under 13 pulls the app into the Families program with much stricter rules. A learning game can still honestly target 13 and up.
→
Closed testing. New personal accounts must run a closed test with at least twelve testers who stay opted in for fourteen consecutive days before production access is even possible. This is the slowest part of the whole launch, and it depends entirely on other people.
Practical tip Switch the Play Console to English by adding ?hl=en to the URL. Every guide and forum answer uses the English labels, and the localized menus are reorganized just enough to get lost in.

Where It Stands

The web version is live, payments work end to end, and the Android closed test is in review with Google. Next is collecting testers, running the fourteen days, and applying for production. The lesson I keep relearning: the code is maybe half the work of a product. The other half is trust plumbing, the payments, email, signatures and declarations that let strangers rely on it.
